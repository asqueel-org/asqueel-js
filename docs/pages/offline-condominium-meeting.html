01 / THE SCENARIO

One meeting, a bounded set of data

The property manager's system runs on Python, uses Gramlot for the interface and keeps its data in the central database. The meeting takes place in a room where the connection is missing or unreliable. Whoever takes the minutes must still read the documents, register who is present, collect the votes and write the resolutions.

Before the meeting a package is prepared for that meeting only: the people involved, the units, the thousandths tables, the agenda, the budget data and selected documents. It is a fairly small set, with a precise initial version and a well-defined working period.

The unit of work is the meeting. The system hands its records to one operator for the session. The operator works locally and returns a consistent result at the end of the meeting. Assigning the work and acquiring the result are handled by the application.

A Gramlot demo is available, with tabs for the phases of the meeting, a participants drawer, discussion, vote and a minutes block for every agenda item. Five fictional documents are included; the rules for real decisions are still to be added.

  1. Prepare the package. The server exports the model source, also limited to the useful tables, and the records in TYTX. It includes the model dependencies and the related data. The documents needed in the room are downloaded before leaving.
  2. Open and check the app. The browser rebuilds the model, creates the SQLite database and imports the data. The operator checks meeting, date, participants and the availability of the attachments.
  3. Run the meeting. Attendance and proxies, entries and exits, votes, notes and resolutions are recorded. The app updates its views and saves the records in the local database.
  4. Resume the work. Reopening the same workspace recovers the data already changed. The initial package prepares the work; resuming reads the existing database.
  5. Return and acquire. The app exports data and attachments. The Python system verifies them, links them to the meeting and applies its own acquisition rules. A confirmation states that the work was received.

The return can travel as a file or, when the connection is back, through an application command. An identifier of the package and of the return lets the system recognize a repeated submission.

03 / DATA AND MODEL

Bring into the room what is needed

The model can be written in Python. Its declaration travels as the recipe source in TYTX; Asqueel JS uses it to rebuild the supported tables and relations in the local database. The central database can keep its own engine: the transferred package uses the SQLite-compatible projection.

Bags for structured content

A Bag can hold sections of the minutes, notes and extra attributes. TYTX keeps the structure and the supported types between Python and JavaScript.

Blobs for documents

PDFs, images and other files can travel as binary data. To read them offline their bytes must be brought along: a link to a document on the server still needs the network.

Selecting the data stays with the application: choosing some tables does not decide which records and attachments are needed. For large documents consider the size of the package and the capacity of the device.

04 / VOTES AND CALCULATIONS

Share the formulas, keep the context

Thousandths totals, attendance summaries and vote aggregations can be expressed with the declarative formulas and the queries the compiler supports. The same declaration is then interpreted in Python and in JavaScript, and SQL and results are compared on the application cases.

Python functions are not translated automatically. The rules for proxies, participation, quorum and outcomes must be defined and validated in the application layer. When they need procedural code, that code must also exist in JavaScript or be expressed through the supported shared declarations.

Every vote keeps its own snapshot. It records the participants and the represented parties, the weights actually used and the version of the rule applied. A later entry updates the current situation without changing the basis of a closed vote.

A purely arithmetic example

A vote records 420 thousandths in favour, 180 against and 60 abstaining: the represented total is 660. If a person then enters with another 20 thousandths, the current situation becomes 680; the summary of the earlier vote keeps its 660.

These numbers illustrate state preservation and counting. Quorum and outcome need the rules of the specific decision, including any per-person counts. The model must distinguish people, units and shares.

05 / THE SERVERLESS APP

The work happens in the browser

Gramlot provides the interface. Asqueel JS rebuilds the model and compiles the queries. SQLite, running as WebAssembly, reads and writes the data; IndexedDB keeps the database in the browser. No reachable application server is needed during the local session.

ONE HTML FILE

An app opened as a file

The Gramlot serverless exporter can embed interface, runtime, worker and SQLite in one HTML file opened through file://. Model and data can be loaded from a separate package.

Changed records stay in the browser profile; they are not written back into the HTML. In the PoC the file path identifies the workspace: export and import move the work to another device or path.

APP PREPARED ONLINE

An address reopened offline

The app can be served over HTTPS and prepared for offline use, caching resources and data before the meeting. A PWA can add a start from the home screen.

A complete PWA installation and the behavior on the chosen devices need dedicated verification. Resources and attachments must be available where the work will happen.

Computers and tablets: what was verified

The single-HTML cycle was verified on desktop Chromium, with the network disabled and a full browser restart. On desktop Safari 27.0.1 loading, changes, closing and reopening the tab and the comparison of the return with Python passed, after a fix to how the file is passed to the worker.

On Safari a full restart, a disconnected network and the manual file selection and saving remain to be verified. A tablet is a possible device for this scenario, but iPad and Android tablets have not been tried yet. The Safari checks concern the transfer PoC; the meeting demo was verified in Chromium, also on simulated small screens.

06 / FROM THE TECHNICAL BASE TO THE APPLICATION

From the small PoC to the complete meeting

Try the Gramlot page. Run npm run build:assembly, then open output/assemblea-offline.html. The minutes unlock with the padlock: leaving the field updates the Bag and saving keeps the text offline. The page also guides the assignment of proxies and shows the votes still to record. The test compares 86 actions with Python, restarts Chromium without network during a vote and verifies the exported package.

The available base covers the transfer of the model, the creation of the local database, reading and writing records, persistence and an export verifiable in Python. The composed source in TYTX, the migration JSON, the SQLite structure and the values were compared; Bags and blobs have dedicated tests on Chromium.

The PoC already includes a model with 24 participants, an editable agenda, five fictional documents and Gramlot screens for attendance, proxies and votes. Completing the application needs the participation and voting rules of the real cases, refined minutes and the acquisition command in the management system. PDF generation and signatures are features to add. The application rules invoked during a write must also be connected explicitly: the query editor of the PoC writes directly through the compiler.

  1. Prepare a sample case in Python. A meeting with units, participants, thousandths, an agenda and a few documents.
  2. Run it in the browser without network. Record a proxy, an entry, an exit, two votes and a draft of the minutes.
  3. Close and resume. Check that attendance, votes, notes and documents stay available on the chosen device.
  4. Return the package to Python. Compare structure, records, attachments and vote calculations; acquire the work once and confirm its receipt.

The expected result: the manager prepares one meeting in the system, holds it also without a connection and brings a complete, verifiable set of results back into the central system.
