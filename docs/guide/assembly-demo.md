# Offline meeting demo

A self-contained Gramlot page for an Italian condominium meeting ("assemblea
condominiale"), built with the official serverless exporter and packed into one HTML
file. The model is declared in Python and exported as a TYTX source: the app creates
SQLite in the browser, uses model formulas for representation and aggregates the votes
through the compiler. The worker and the WASM are embedded; it needs no server and no
first online start. The user interface is in Italian.

```sh
npm run build:assembly
# Open output/assemblea-offline.html with file://.
```

## Manual walkthrough

1. In the **Costituzione** tab, register Anna Rossi, Luca Bianchi and Marta Verdi as present.
2. Give Paolo Neri's proxy to Anna: 3 present, 4 represented, 215 thousandths.
3. In **Ordine del giorno**, open "Bilancio preventivo". The **Lavori** stack offers
   topic, discussion, vote and minutes. In the discussion press **＋**, choose the speaker,
   write and press **Registra**; the administrator has a dedicated button. Then open the
   vote. Attendance and proxies are locked until the vote closes.
4. Record Anna and Paolo in favour, Luca against, Marta abstaining.
5. Close the vote: 110 in favour, 55 against, 50 abstaining. The demo rule approves it.
6. Unlock, write and save the minutes block; **Concludi punto** makes it read-only.
   **👥 Partecipanti** opens the participants drawer from every tab.
7. Close the browser, also during a vote, and reopen the same file with the same profile.
8. **📤 Esporta** downloads the model and the TYTX records. **Nuova prova** asks before
   replacing the workspace.

## Scope

- 24 fictional people, one share each, integer thousandths totalling 1,000.
- Direct proxies from an absent person to a present one, revocable between votes.
  No self-proxies or chains. Leaving the meeting suspends the proxies held.
- One open vote at a time. The roster, representative and weight are copied into the
  vote records when the vote opens. Every represented person has a distinct choice,
  also through a proxy. Choices can change until the vote closes; closing needs all of them.
- A demonstration rule only: in favour strictly above half of the represented
  thousandths. No legal quorum, proxy limits, co-ownership or special tables.
- Five initial agenda items, editable and extensible, reordered by drag and drop or from
  the keyboard. Each item has a discussion of interventions (author, text, time), one
  vote and a minutes block. Five fictional HTML attachments are stored in SQLite.
- Application actions are transactions: a failed vote opening leaves no partial header
  or votes. Drafts stay in the Data Bag until saved; export and closing ask to save or
  discard them first.

The database lives in IndexedDB, not in the HTML file; the path selects the workspace.
The server takes the snapshot according to its own rules; there is no automatic
synchronization.

## Comparison with Python

```sh
$PYTHON scripts/assembly_oracle.py
node --test test/assembly.test.js
bun test test/assembly.test.js
npm run test:assembly
$PYTHON scripts/assembly_oracle.py --verify-return output/assembly-browser-return.json
```

The rules are implemented separately in Python and JavaScript; the model and the
declarative read requests come from the reference. 86 actions compare the composed
source, the migration JSON, the SQLite catalog, SQL, parameters, records, counts and
errors. The sequence contains approved and rejected votes, revocations, entries and
exits, discussions, minutes blocks and a vote left open. Other tests simulate storage
errors while opening a vote and while saving the agenda, and check the full rollback.
An upgrade test keeps the data of earlier workspace versions (fixtures v1 to v4).

The Chromium test starts offline, restarts the browser, reads the partial vote back and
exports a real file, which Python imports and recomputes. The page is not qualified on
Safari or physical tablets.

## Sources

- `scripts/assembly_oracle.py`: Python model and rules, reference generation, return verification.
- `scripts/assembly_demo.py`: 24 names, thousandths and five fictional documents.
- `examples/assembly-seed.json`: initial bundle and declarative reads generated by Python.
- `browser/assembly-domain.js`: JavaScript rules and queries through Asqueel JS.
- `browser/assembly.js`, `browser/assembly-views.js`, `browser/assembly.css`: page and logic.
- `browser/assembly-worker.js`: local execution and persistence.
- `browser/assembly-upgrade.js`: upgrade of earlier workspaces.
- `scripts/build_assembly_html.js`: single-file packaging.
- `test/assembly-actions.json`: the shared scenario; `test/fixtures/assembly.json`: Python results.
