01 / THE USE CASE

Collect orders where the network cannot follow

A business application runs in Python, uses Gramlot for its frontend, and keeps its main database on the server. A salesperson needs to visit customers without a reliable connection. They only need a small working set: selected customers, products, prices, and their own orders.

  1. Prepare the working set. The application selects the relevant model declarations and records. Python exports the source Bag and typed data.
  2. Load it locally. Asqueel-JS reconstructs the model and creates the corresponding SQLite tables in the browser.
  3. Work offline. The user creates orders and order lines, reads reference data, and edits their records. Work survives closing and reopening the browser.
  4. Return the work. The browser exports a typed snapshot. The Python application receives it through a file or, when connectivity returns, an application endpoint.
  5. Apply it to the business database. Application code decides which returned records to insert or update and acknowledges completion.

The assumption is simple: the user owns the records they are working on during the offline session. Record selection, ownership, permissions and write-back belong to the application. This work supplies model transfer, local execution, persistence and a verified return format.

The current deliverable is a transfer playground with a JSON query editor. A customer-facing order-entry screen and its server-side write-back endpoint are the next application layer, not features already delivered by this demonstration.

Gramlot runs the page through its browser/worker environment. Asqueel-JS rebuilds the transferred model, renders migrations and compiles queries. SQLite compiled to WebAssembly actually executes the SQL. Its files are persisted through an IndexedDB-backed VFS; IndexedDB is the storage layer, not a substitute SQL engine.

The transfer envelope contains a real SourceBag serialized as TYTX, plus TYTX record streams keyed by qualified table name. The source can cover the full model, selected packages, or selected tables. Required relation targets must be included; the exporter does not silently remove relations or fetch extra server records.

The Python exporter produces a SQLite-compatible projection of supported declarations: database implementation becomes SQLite and package schemas map to main. It preserves SQL names and detects collisions. The original Python builder remains unchanged. Connection settings, Python table classes and executable Python functions are not transported.

Typed values, not just JSON strings

TYTX preserves the distinctions needed by the transfer: booleans, dates and times, decimal representations, text, NULL, nested Bags and binary data. Bag node labels, tags and attributes are retained; empty Bags, empty blobs and NULL remain distinct.

SQLite still has its own numeric limits. Transporting a Decimal does not make SQLite NUMERIC an arbitrary-precision decimal store. Unsupported or unsafe values are rejected within the supported transfer contract.

Durable local workspace

The browser stores both the SQLite database and the source needed to reconstruct its builder. On reopening, it reads existing records rather than importing the initial data again.

The HTML itself is never rewritten. Data lives in the browser profile. In the single-file demo, different file paths select separate workspaces; use export/import to move work to another path or device.

Import loads snapshot records in a transaction with explicit NULL values and a final foreign-key check. A data failure rolls back imported rows; schema migration is a preceding transaction. The Python receiver used in verification imports into an empty staging SQLite database. It does not merge a snapshot automatically into the remote business database.

Python reference: Asqueel 0.6.1 with the pinned fix for issue #44. This report describes the tested transfer path; it is not a claim of complete Python/JavaScript feature parity. The demo query editor performs direct compiler writes; required application hooks must be provided through the appropriate JavaScript application API.

03 / DELIVERY

Two ways to run without a live server

HOSTED OFFLINE APP

Open once, then work offline

Serve the application over HTTPS, or localhost for development. A versioned service worker caches the HTML, JavaScript, Gramlot themes, workers and SQLite WASM. Once the app reports that it is ready, the user can disconnect and reopen the same address.

No reachable server or local server process is needed while working offline. New asset versions wait for old application tabs to close.

This is the basis for PWA delivery. The evidence here covers cache-based offline startup; a complete Home Screen installation flow and tablet qualification remain product work.

SINGLE HTML FILE

Open directly with file://

The official Gramlot exporter packages the page, logic, runtime and styles into one HTML document. We also embed the SQLite worker and WASM bytes. Workers start from in-memory Blob URLs.

The resulting file is approximately 5.9 MB. It needs no companion files, service worker, local server or initial online visit. Loading data and exporting results use ordinary file controls.

Verified on desktop Chromium. Reopen the same file path using the same browser profile to recover the existing workspace.

Here, “serverless” means that the client can execute the application locally. A Python server can still prepare data beforehand and receive it afterwards; no cloud function platform is required.

04 / EVIDENCE

A complete cycle, executed rather than simulated

The single-file test copies only the exported HTML into a separate temporary folder and launches a fresh Chromium profile with networking disabled from the start. It loads a Python snapshot, reads and changes records through the page controls, inserts an order line, inserts and deletes a temporary row, and verifies the result.

It then terminates Chromium completely, starts a new process with the same profile, reopens the local file while still offline, and downloads the resulting snapshot. No external HTTP, HTTPS or companion-file request is permitted during the main cycle. Python then imports the actual downloaded file.

Real Safari 27.0.1: local HTML round trip

The HTML was also tested in desktop Safari through Apple's built-in MCP automation. Python model and data loaded into SQLite; update, insert, delete and select worked. After closing and reopening the application tab, IndexedDB restored the workspace. The complete model, migration JSON, SQLite catalog and values matched the Python reference. Python then accepted the actual exported snapshot, including its TYTX types.

The test exposed a Safari limitation: reading a File after sending it to a Blob worker failed with NotReadableError, although reading it in the page succeeded. The page now reads the selected file and sends its text to the worker.

Scope: the application tab was reopened within one automation session; a full Safari process restart and physically disconnected networking were not tested. The automation supplied Python file bytes to the normal file input and captured the Blob produced by the export button; the OS file picker and saved download were not validated. This Safari case covers ordinary records; the separate Bag/blob test above ran in Chromium.

05 / TABLETS

Could this run on a tablet?

Yes, the architecture is suitable for a tablet application. The recommended next delivery route is an HTTPS-hosted offline app, with a Home Screen/PWA experience where supported. This is a feasibility assessment, not a tablet compatibility certification.

The required platform features include WebAssembly, workers, IndexedDB and Web Locks. WebKit documents Web Locks in Safari 15.4, including worker use; this supports the feasibility of the design on iPadOS, but does not prove this SQLite VFS and application combination on a real iPad. WebKit: Safari 15.4 web APIs.

The offline assets and workspace must be prepared in the context in which the user will actually work. Apple: websites as iPad apps; MDN: installable PWAs.

The next tablet acceptance test

Use a real Android tablet and a real iPad: prepare the app and data, enable airplane mode, enter orders with the touch UI, force-close and reopen, then export or reconnect and send the records back to Python. Check file selection/sharing, background suspension and storage persistence in the chosen browser or installed-app context.

The product should expose export and recovery actions and handle storage failures. WebKit describes persistent-storage requests and eviction policy; persistence should be validated rather than assumed from the presence of IndexedDB. WebKit: storage policy.

06 / REPRODUCE & EXTEND

Try the single-file workflow

From the asqueel-js repository, with its dependencies installed:

npm run build:file
# Open output/asqueel-offline.html in Chromium using file://

npm run test:file
.reference/venv-current/bin/python scripts/transfer_oracle.py \
  --verify-return output/file-transfer-returns.json

The final command requires the repository’s configured, pinned Python reference environment. The browser does not run Python; that command verifies the file the browser returned.

To repeat the Safari check on macOS with Safari 27 or newer and remote automation enabled:

python3 scripts/test_safari_file.py
.reference/venv-current/bin/python scripts/transfer_oracle.py \
  --verify-return output/safari-transfer-returns.json

In the page, download the Python example, select it, and choose Carica in SQLite locale (load locally). Execute a JSON request, close the browser and reopen the same HTML file. Choose Esporta snapshot per Python to download the result.

{
  "operation": "update",
  "table": "work.document",
  "values": {"id": "d1", "title": "Modificato offline"}
}

This is the update used in the parity scenario; the automated test also inserts a related line and exercises reading and deletion. Arbitrary user edits are exported normally, but are not expected to match that fixed test scenario.

From the demonstration to order collection

Build Gramlot customer, product and order forms on top of the local model. Let the Python application select the initial working set and register the returned orders according to its own business rules. Add explicit “prepared for offline work” and “submitted” states, then qualify the chosen devices. The model-transfer and storage mechanisms demonstrated here can remain the same.
